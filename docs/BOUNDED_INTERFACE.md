# Saved-place AI interface

Updated 2026-10-20. The main input can use AI to interpret the user's start, activity, time and supported constraints before local retrieval and grounded selection. Earlier three-scenario results are recorded separately in [live interface evidence](LIVE_INTERFACE_REVIEW.md).

## Start

Without activation, `node scripts/app/start-bounded.mjs` serves local search and an optional technical evidence preview at `http://127.0.0.1:3003`. It does not read credentials or create an allowance. Both modes use ignored `data/runtime/offline-app.json`; a clean checkout needs authorized local data/configuration provisioning. Tests use authored synthetic records.

The user's standing preference is **AI enabled by default**. Restart the current private interface with:

```powershell
node scripts/app/start-ai.mjs
```

This loads the existing ignored `data/runtime/ai-default.json` choice. It points to a separately prepared **100-request** allowance, valid until **2026-11-18T16:01:59Z**, and the server-only environment file. All **11 prior attempts** remain counted in the linked history. The allowance is finite because the user previously asked not to spend all credits; the account balance is unknown. It is a request ceiling, not a monetary guarantee. Restarting does not replenish it. Missing/expired configuration fails startup explicitly instead of substituting local-only mode. This preference does not turn on background calls or automatic retries.

Preparation is an operator action: `run-pilot.mjs prepare-ai-default <new-private-directory> <exhausted-prior-directory>` verifies prior exhaustion and fingerprints, then creates a new allowance exclusively. The private startup choice has `schema_version: 1`, an absolute `activation_file`, and an absolute `env_file`; it must refer to that reviewed activation. Normal startup never creates or repairs accounting. Credentials, source IDs and budgets stay outside Git. Historical pilot preparation retains three attempts / six hours. The separate legacy `npm start` command does not use this setup; use `node scripts/app/start-ai.mjs` for this demo.

## User flow

Text interpretation is separately activated on an already configured AI installation with `node scripts/app/enable-text-interpretation.mjs --enable-text-interpretation`, followed by restarting the AI server. This changes only the ignored activation's `interpretation_enabled` flag; it does not reset the ledger, create an allowance or make an API call. The user-visible disclosure must accompany this capability because typed text now reaches OpenAI.

1. Type an outing, for example “I am near Mega and want to go for a walk for 20 minutes.” The start/scenario/time/filter controls are collapsed and optional. Explicit text overrides the corresponding settings for this search; omitted fields use those settings. Results show the understood start, activity and time without rewriting the saved manual controls. Named starts support Mega Silk Way, Bayterek and Zhetysu Park; unknown/ambiguous starts ask for clarification. A selected map point can be used by saying “from my selected point.” Exact destinations, price/dietary requirements, driving and multi-stop itineraries are unsupported.
2. Click the main AI button. Interpretation sends only typed text and language, with decimal coordinate-like text redacted. Names/addresses in that text can identify an area; do not enter personal information. Strict schema validation constrains the output, and known landmark coordinates are resolved locally. Local retrieval and deterministic eligibility checks then run. The separate recommendation call sends at most five candidate names, categories, approved descriptions, coarse estimates and structured filters. Its body excludes raw query, coordinate fields, stable IDs and the full dataset.
3. Read up to three alternatives with estimated travel/visit times, activity ideas, source facts and uncertainty. The model selects retrieved evidence and allowed reason/activity codes; application templates provide the wording.
4. Suggestions appear below the input and as matching numbered pins. Select a card or pin to calculate a walking route from the resolved starting point. Changing inputs clears stale suggestions/routes. A short budget may produce no eligible places; it is never silently enlarged. See [map-interface behavior and verification](MAP_INTERFACE.md).

The active AI interface needs no separate payload preview or checkbox. The disclosure stays beside the button. Inputs are locked during a live request and their previous states restored after budget refresh. A nonempty text search spends at most two attempts from the same existing allowance: one interpretation and, only when candidates exist, one recommendation. Empty text uses manual settings without an interpretation call. Clarification stops after interpretation. Failed attempts remain counted; no automatic retries. AI remains the configured main action even if temporarily unavailable, expired or exhausted; the state is explained instead of silently changing the endpoint. Generation failures may return a labeled retrieval-only fallback; interpretation failures return an error. Device geolocation is disabled. [OpenStreetMap](OPENSTREETMAP.md) loads on opening; selecting a suggestion sends rounded endpoints to FOSSGIS / Valhalla independently of AI accounting.

## Server boundaries

`POST /api/recommend-ai` runs optional bounded interpretation, retrieval and bounded generation. `/api/recommend` remains local. The technical `/api/generation/preview` and `/api/generation/confirm` routes remain available for development but their panel is hidden in the activated UI. All generation routes require JSON, the exact same Origin, a validated loopback Host and the random `X-Qadam-Preview` token from `/api/config`. Browser inputs cannot change model, authorization or allowance. Public config exposes readiness, the running `generation_model`, `interpretation_configured` and remaining requests, never keys, paths or record IDs. The smoke helper requires the running model to match activation before making a paid call, preventing stale-server model attribution. Responses are `no-store`.

The preview workflow retains one body for two minutes and consumes its token once. Main-button generation invalidates old previews. The persistent ledger reserves before each dispatch, allows one in flight, and never refunds failed or uncertain calls. The browser allows 145 seconds with interpretation (75 otherwise), covering two provider deadlines and retrieval; cancellation does not undo a reservation. Source data and user text are untrusted, never executable instructions. Neither typed requests nor interpretation responses are stored in the ledger.

## Verification and handoff

Faster-model checkpoint (2026-10-20): the active demo switched from `gpt-5.4-mini` to **`gpt-6-luna`**, using `reasoning.effort: "none"` for both interpretation and selection. [Official model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna) confirms support for Responses, structured outputs and this effort level. One live simulated Bayterek coffee/45-minute search completed in **4.776 seconds**, correctly interpreted the text and returned **two grounded alternatives** within the budget. It used two requests; the current allowance moved from 83 to 81 remaining. This is one observed end-to-end sample, not a latency guarantee or controlled comparison.

The retained operator command is `node scripts/app/switch-ai-model.mjs --model gpt-6-luna`, followed by server restart. It writes a separate model approval bound to the original authorization hash and expiry, then atomically updates activation. Original authorization, budget manifest and all attempt files are preserved; both models share the same lock and finite ceiling. No model change can replenish requests. `node scripts/app/check-live-search.mjs --run` is an explicit, paid smoke check (up to two calls), saving aggregate results only under ignored `data/runtime/`. Do not run it as an offline test.
